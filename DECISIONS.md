# Decisions Log — autonomous choices made during the build, with brief rationale.

## Phase 1 — Supabase schema + RLS + seed

- **Single-gym scope, but multi-gym-ready shape.** Every domain table carries `gym_id`.
  The seed creates exactly one gym row (`gyms`) holding all white-label branding, so the
  system is rebrandable by editing one row and never touching code. Keeping `gym_id`
  everywhere avoids a future migration if a second gym is ever added.

- **`profiles` is the auth/role bridge.** `profiles.id = auth.users.id`. It holds
  `role` (super_admin | reception | member), `branch_id` (for reception scoping), and
  `member_id` (links a member login to their `members` row). RLS reads this table via
  `SECURITY DEFINER` helper functions to prevent recursive policy evaluation.

- **Phone uniqueness = per gym.** `UNIQUE (gym_id, phone)`. Phone is the primary human
  identifier; validated to Saudi format in the app layer (a light CHECK exists as a guard).

- **Human-readable `member_code`** generated by a per-gym sequence + trigger (`M00001`…),
  separate from the UUID PK, because reception searches/prints by it.

- **Subscription lifecycle** is an enum `pending | active | frozen | expired | cancelled`.
  `end_date` is the source of truth for expiry (timezone handled in app as Asia/Riyadh).
  Renew/freeze/upgrade are implemented as Postgres RPC functions (Phase 3) so the same
  logic runs regardless of client and can be covered by RLS `SECURITY INVOKER`.

- **Payments kept gateway-agnostic.** `method` (cash | mada | online | other) plus generic
  `provider` / `reference` text columns so an online gateway drops in later with no schema
  change. `receipt_number` is unique per gym.

- **Notifications table doubles as the dev outbox.** A `status` of `simulated` means "logged
  only, not actually sent" — the notifications engine (Phase 5) writes here; a real provider
  (Twilio / Meta WhatsApp) later flips these to `queued`/`sent`.

- **Site content is data-driven.** `trainers` + a generic `site_content` (key → JSONB) table
  hold hero copy, testimonials, FAQ, gallery, facilities — so the public site (Phase 7) is
  fully editable from the DB.

- **RLS everywhere, deny-by-default.** RLS enabled on every table; no policy = no access.
  Super admin: full access within their gym. Reception: read/write scoped to their
  `branch_id`. Member: read-only to their own member row + own subscriptions/payments/
  check-ins, plus create a `pending` renewal request. Public marketing tables
  (`gyms`, `branches`, `plans`, `trainers`, `site_content`) are readable by `anon` for the
  public website; everything member-specific is not.

- **Migrations split for readability:** `0001` schema (extensions/enums/tables/triggers),
  `0002` RLS (helpers + policies), `0003` storage bucket + placeholder RPCs. `seed.sql`
  loads demo data (1 gym, 2 branches, 4 plans, ~50 members with mixed statuses, payments,
  check-in history).
